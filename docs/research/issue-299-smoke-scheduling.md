# Issue #299 research: bounded installed-wheel smoke scheduling

Date: 2026-10-11. No new CAL HTTP requests.

## Grounded source audit
- `src/cal_mcp/stdio_live_smoke.py` has 12 fixed cases, one zero-CAL Unicode conversion and 11 CAL-backed cases. One text-page follow-up is bound to the exactly returned text-search identifier and is skipped on failed parent. Calls are sequential, no enumeration, within one `Client(StdioServerParameters)` connection. `evaluate_smoke_cases` directly invokes the next tool after the previous call finishes, without any inter-case schedule.
- `src/cal_mcp/server.py::app_lifespan` constructs an explicitly scoped smoke client with `max_concurrency=1`, `max_retries=0`, three-second minimum transport spacing, **eight actual starts per rolling 60 seconds**, and a separate `SmokeAttemptBudget(max_attempts=25)` counting at the transport boundary. A single CAL-backed case can use multiple CAL requests; there is no client-facing per-tool counter until shutdown. The runner reads only the final 25-cap report from a private file and must not mistake its absence for zero.
- A nonzero bounded inter-**case** delay of 60 seconds measured **from completion** of the prior CAL-backed tool to the start of the next ensures every prior tool's transport starts have aged out of the 60-second rolling window before another tool call starts. It does **not** protect against an individual tool performing >8 requests inside one call; that must remain a visible failed acceptance. It can be optimized later only after proving exact worst-case per-tool transport bounds. There is no need to expose private budget state as an MCP tool or change production client policy.
- There are 11 network-backed cases, thus at most ten such waits, each <=60 seconds, total <=600 seconds of harness sleep for the fixed matrix; canceled waits propagate. Empty/missing tools, unsatisfied dependent cases, and `cal_convert_to_code` need no CAL cooldown and must not consume a between-case interval. The harness must never retry a locally refused call in a tight loop. Never trust upstream-provided Retry-After as scheduling permission.
- `_ERROR_ENVELOPE_SCHEMA` in `stdio_live_smoke.py` is out of sync with `PublicErrorKind.LOCAL_RATE_LIMIT` introduced in #297; currently it misclassifies the honest local refusal as malformed harness output. Recognize that exact typed kind and classify as nonpassing `unavailable`, fail-stop to avoid repeated instrumented tool calls after local admission fails.
- Both `.github/workflows/live-smoke.yml` and release.yml live-smoke jobs have `timeout-minutes: 10`. This can time out a correctly slowed >10-minute suite; increase to 30 minutes to cover <=10min gaps plus bounded at-most-25 transport attempts of 15s each and wheel install/setup.
- The weekly live-smoke workflow currently has a cron schedule, which would launch real CAL traffic automatically on Monday even though #262's observed 429 and 37-token zero429 release gate remain unresolved. Disable **automatic cron**, retain `workflow_dispatch` for deliberately authorized runs, and retain tag-release fail-closed gating (do NOT tag until approved). Existing `test_release_smoke_workflows.py` currently asserts schedule exists and requires a test-first update.

## Safety and limitations
- 60s inter-case schedule is a transparent deliberately slow precaution, not an upstream-approved quota or a successful 37-token acceptance. A permitted CAL attempt may still receive HTTP 429; on such a response the suite must remain failing.
- No production MCP tool names, response formats, CAL corpus ingestion, cross-process coordination, or 25-attempt cap changes.
- All CI coverage must use fake clock/sleep and mock MCP results, including abort/cancellation, bounded skips, and no accidental network. Normal CI stays offline.
